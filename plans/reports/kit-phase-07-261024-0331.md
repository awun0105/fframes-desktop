## What was built

- **`components/fframes-kit-macros`:** a proc-macro crate that depends only on `proc-macro2` and `quote`.
  - Both are pinned like `svgr-macro`'s, because the root workspace does not pin them. `syn` is not needed: the macro walks tokens and parses nothing.
  - `fframes_kit::ui!` and the prelude re-export the macro by name.
  - The `ui` module and the `ui!` macro coexist, like `std::vec` and `vec!`.
- **The rewrite, in `tags.rs`:**
  - `<` followed by one identifier that starts uppercase opens a component tag. Every other token, SVG tags, text, `{expr}` blocks and lowercase closing tags, is copied through unchanged.
  - A tag becomes `{ let props = Name { fields, ..ui.defaults() }; ui.show(props) }`, and the markup goes to `::fframes::svgr!`.
  - When the whole input is one component tag, the macro emits that block alone and does not rely on how `svgr!` treats a bare `{expr}` root.
  - `svgr!` parses brace blocks with `Block::parse_within`, so the statement form works inside markup.
- **Children:** a tag's children become `children: ::fframes_kit::ui::children(move |ui| ::fframes_kit::ui!(<g>..</g>))`. Nested tags therefore expand through the same macro.
  - The closure parameter `ui` and every `ui` the macro emits carry the tag name's span. The inner tags therefore resolve to the container's `ui` and its local time.
  - Only the `props` binding uses `Span::mixed_site()`, so it cannot collide with the caller's names.
  - Tags of the same name nest correctly.
- **Errors** point at the token they are about:
  - a dashed attribute, at its first identifier, with the field name;
  - a missing `/>` or closing tag, at the tag name;
  - a stray `</Name>`;
  - a value that is not a literal or a block.

  Each gives exactly one compiler error. The first version emitted `compile_error!(..);` with a semicolon, which added a second error, "macro expansion ignores `;`"; the semicolon is gone.

## Departures from the phase file, with reasons

- **The missing-`ui` note is not implementable as written.** A proc macro cannot see what is in scope, and it cannot add a note to rustc's "cannot find value" error.
  - What is done instead: every `ui` the macro emits has the tag's span, so the error ("cannot find value `ui` in this scope") lands on the first tag.
  - The guidance sentence ("create one with `let mut ui = Ui::new(frame, ctx, &self.theme)`") is in the `ui!` docs and in `components.md`, next to a `compile_fail` example.
  - The advisor agreed.
- **Literal values.** A uniform `.into()` cannot work for numbers: `f32` and `usize` have no `From<i32>`, so `{3}.into()` fails to infer. So:
  - a quoted value, or any `{expr}`, goes through `.into()`;
  - a number or `true`/`false` alone in braces is written as is, so the field's type decides it;
  - a bare attribute is `true`.

  `components.md` says that quoted values suit text fields. The gallery test confirmed that `cy="180"` does not compile for an `f32` field.
- **No lint noise in callers' code.** Expanded code carries the caller's spans, so clippy reported two lints in the gallery's tag code:
  - `useless_conversion`, when an `{expr}` already has the field's type;
  - `needless_update`, when every field is set.

  The macro now converts through a hidden generic `fframes_kit::ui::__prop(value)`, which the lint does not inspect. It also marks the `props` statement `#[allow(clippy::needless_update)]`. Workspace clippy under `pedantic` is clean with the gallery's tags.
- **The containers are `Themed` now.** Tags always emit `..ui.defaults()`, but no container implemented `Themed`. `Sequence`, `Loop`, `Freeze`, `Fill`, `Canvas`, `SceneFade` and `Appear` now default to empty children (a crate-private `no_children()`) and to the values their constructors used:
  - `Sequence`: from 0, no end;
  - `Loop`: 1 s, forever;
  - `Freeze`: at 0;
  - `Fill`: no background;
  - `Canvas`: `Space::FULL_HD`;
  - `SceneFade`: the theme's fast fades, and `new` now builds on it;
  - `Appear`: from 0, about the middle of 1920x1080. Its private 4-argument `themed` was renamed `with_theme`.

  `LaggedStart`, `AnimationGroup` and `Succession` hold a `Vec<Children>` and keep the struct form; `components.md` says so.
- **The integration test lives in `components/gallery/tests/tags.rs`**, not `fframes-kit/tests/`. A real `Ui` needs an `FFramesContext`, which comes from a `Previewer`. That needs fframes' renderer features and the gallery's media, which only the gallery has.
  - The test renders a probe video in tag form and in struct form at frames 0, 20, 40 and 59. Each compares the full element trees `Svgr` prints.
  - The probe uses a lower third, axes with a bare `tips`, and a `Sequence` with a circle and a `rect` as children.
  - It also checks that the circle appears inside the sequence and is gone after it, so the equal trees are not both empty.
- **The `FadeIn` twin.** `FadeIn` is a modifier (`apply`), not a component with children, so its twin puts the card-building code inside a `<Fill>` tag. The cards are extracted into `fade_in_cards`, and the struct scene keeps its exact tree.
  - The `SquareToCircle` twin is all tags: two `<Sequence>`s, a `<Square>` with a `Create`, and the morph as an `{expr}` child.
- **`components.md`'s tag-form section** sits after "Your own component", and the struct form stays the documented way. It covers:
  - the attribute rules;
  - children and the `Fn` closure: build content inside it, and capture only `Copy`, `'a` or reference values;
  - the `Vec` containers.

  It has one compiling example and two `compile_fail` examples (dashed name, missing `ui`). The compiling example is the corrected form of both. I compiled both bad cases in a scratch file, since deleted, to see their messages: the dashed error points at `min-width` with "write `min_width`", and the missing-`ui` error points at the tag.
- **`lib.rs`:** the Remotion table has a JSX row pointing to `ui!`.

## Unresolved

- **The missing-`ui` guidance is in the docs, not the compiler message.** rustc's own error lands on the tag, and no stable mechanism can add a note to it.
- **A quoted value cannot fill a number field.** `cx="320"` does not compile and `cx={320.0}` does. A string parser for number fields would need the field's type, which the macro does not know.
- **Containers whose children are a `Vec`** (`LaggedStart`, `AnimationGroup`, `Succession`) have no tag form for their children. Their children can be passed as `children={vec![..]}` with the struct-form closures.
