## Slice 2: packaging

- **`just package`** packages `fframes-kit-macros` and `fframes-kit` together, with `--allow-dirty --no-verify --exclude-lockfile`.
- **Why both crates:**
  - `cargo package` first refused the kit, because its path dependencies had no version. `components/Cargo.toml` now gives `fframes-kit-macros` 0.1.0 and `fframes-studio-protocol` 0.2.0, the versions in their manifests.
  - It then failed to lock `fframes-kit-macros` against crates.io, where it is not published. Packaging both members together resolves one against the other.
- **Why no lockfile:** `fframes-studio-protocol` (the optional `studio` feature) is outside the kit's workspace and not on crates.io either, so cargo has nothing to lock it against. A library's crate file does not need a lockfile, so the recipe leaves it out.
- **Result:** both `.crate` files are written to `components/target/package/` (185 files for the kit, 343.6 KiB compressed). `docs/` is not needed, because the doctest `include_str!` is under `cfg(doctest)`.
- **Manifests:** both now have the `repository` field.
- **Version coupling:** `version = "0.2.0"` on `fframes-studio-protocol` means `^0.2`, which excludes 0.3.0. The crate is outside the kit's workspace, and the kit never edits it. When upstream bumps it, `components/Cargo.toml` must follow, or the kit workspace stops resolving. The `fframes` line (`1.3.0`) has the same coupling, but is looser because it is past 1.0.
- **Version:** the kit stays 0.1.0.
- **Publishing:** this would need `fframes-studio-protocol` on crates.io first. Without it, the `studio` feature would also take crates.io fframes, not this fork's. Publishing is not in this plan.
