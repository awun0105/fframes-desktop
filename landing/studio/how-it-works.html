A CONNECTED WORKSPACE

Separate processes.
Clear responsibilities.

The app coordinates the work. Your coding agent edits a draft in its own process. Your video runs in a separate preview worker.

01 / THE EDIT TRANSACTION

A draft goes in.
A revision comes out.

Five stages on the successful path. Scroll to move the candidate through them, or jump to a stage.

01 / CAPTURE

Freeze what
will be checked.

After the agent finishes and its writer is quiet, Studio captures the draft twice. Both captures must match.

A changing working copy cannot become the candidate that passes validation.

02 / BUILD

Build the
captured candidate.

Studio compiles in an isolated copy bound to the project’s managed SDK. The build must identify the candidate it actually compiled.

A cached compiler success alone is not an acceptance proof.

03 / INSPECT

Check the result.
Report the coverage.

The worker supplies inspected and rendered frames, range boundaries, and audio checks. Diagnostics and capability gaps stay in the report.

A compile or validation failure can trigger at most one automatic repair turn. Checks do not guarantee that every frame is correct.

04 / REVIEW POLICY

Apply by policy.
Review by choice.

The default policy applies a validated candidate automatically. Manual review waits for Apply; you can inspect diffs and keep a subset of files.

A selected subset is validated again before it can be applied.

05 / ACCEPT

Write the revision.
Keep a way back.

A journaled file-set transaction publishes the accepted changes. If an outside writer races with it, Studio preserves the variants and stops with a conflict.

Undo and per-file revert pass validation too. Revert is refused if the file changed since.

02 / GROUNDING

From a visible object
to useful context.

When the worker supports object selection, a click uses the object map attached to that exact frame. Topmost paint order wins; cycling reveals overlapping objects.

Stable editor keys identify objects. A source anchor is optional and must be registered by the project; Studio does not infer an exact source location for every pixel.

PROJECT-SUPPLIED IDENTITY

The project registers a stable key and, optionally, an anchor. This excerpt illustrates the API; it is not a complete video. 

let title_key = EditorObjectKey::new(

03 / PROJECT TOOLS

A way to look.
Nine read-only tools.

Studio’s tool broker lets your agent inspect the project and rendered output. These nine tools do not provide shell execution, file writes, or export.

The agent’s own tools can still edit files or run commands, subject to your permission policy. Read-only describes Studio’s broker, not the entire agent.

  • project_contextProject facts
  • selection_contextFrozen task scope
  • source_lookupVerified source snippets
  • timelineScene timing
  • render_frameA rendered frame
  • render_stripA frame contact sheet
  • inspectFrame diagnostics
  • style_contextStyle context
  • build_statusBuild status

04 / PREVIEW READINESS

Prepare the whole revision.
Then switch.

The current build keeps playing while the next one is prepared. Worker, frame, and audio switch together at the playhead, once the revision is ready.

Failed or cancelled builds keep the previous preview. The diagram shows a successful preparation; its spacing does not represent elapsed build time.

05 / WRITER CONTAINMENT

A process boundary.
A condition for capture.

Windows uses a job object; Linux and macOS use a process group with escape checks. If Studio observes a writer escape, its candidate is refused.

Containment is not a general sandbox. Work performed by pre-existing services on an agent’s behalf is outside the observed process group or job.

06 / RECOVERY

Keep the accepted revision.
Retain the unfinished work.

After a crash, Studio recovers to the last accepted revision, marks unfinished work interrupted, and offers the retained draft. Process exit is not proof of a successful build or apply.

An older Studio file format is refused and left unchanged. Studio does not silently migrate it.
